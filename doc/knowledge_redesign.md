## 1. 架构定案

### 1.1 两个知识平面 + 一层证据

| 平面 / 层 | 路径 | 供给方式 | 消费方式 |
|---|---|---|---|
| 环境事实（知识平面） | `memory/MEMORY.md` · `memory_summary.md` · `fact_meta.json` · `curator_metrics.json` | **自动**：成功任务收尾蒸馏 | **常驻注入**（每步重发） |
| 操作技能（知识平面） | `skills/*.md`（frontmatter + playbook + substeps） | **人工编写**（2026-10-02 起不再自动产出） | **按需加载**：`search_skill` / `load_skill` |
| 任务证据（证据层） | `tasks/<tid>/`（轨迹 jsonl / run.json） | 运行时 | 蒸馏原料、可选重放，**不进注入** |
| 角色卡 | `character.md` | 用户 | 独立注入块，不属知识层 |

**形态由读者决定**：读给模型的（事实、playbook）是引导型文字；`substeps` 读给机器（身份、校验、可选重放），**不进 prompt**。两个知识平面共用一套治理：去重、效用分、容量淘汰。

### 1.2 写入链

每个成功任务收尾触发一次，不拖垮主流程：

```
bridge._curator_after_finish → Curator.run_once
  → 轨迹（脱敏）+ 界面状态摘要 → LLM 提取事实（1 次调用）
  → 语义去重（LLM 判 duplicate / merge / independent）
  → 印证或反证（LLM 勾选条目）→ 写入 fact_meta.json
  → 容量维护（印证 / 反证 / 淘汰）
```

节流（写入端）：单 run ≤ 3 条事实；同一 App 300s 冷却内不重复合并（LLM 调用照常，冷却只挡入库）。

### 1.3 注入与检索

- **常驻注入块**（`build_knowledge_block`）：事实全文 + 技能目录 top-3（LLM 选档，无 brain 保持原序），预算 **2000 字符**，每步重发。
- **按需加载**：`load_skill(name)` 有 playbook 返回文字引导；`search_skill(query)` 与目录共用同一选档实现。命中即记 `total_uses`（簿记）。
- **可观测**：knowledge 事件上报 memory / skills / chars 与**本次注入的事实清单**；知识页支持列表 / 启停 / 删除 / 合并 / 导出。

### 1.4 容量边界（手机端常量）

| 对象 | 上限 | 治理 |
|---|---|---|
| 事实 · 单 App / 全局 | 12（保底 3）/ 40 | 效用分排序淘汰 |
| 技能 · 全局 | 20 | 同上 |
| 注入块 / memory 视图 | 2000 / 20000 字符 | 硬上限（约束效率，不是磁盘） |
| rollouts / tasks | 最近 30 条 / 50 run・7 天・100 MB | 收尾清理 |

效用分 = 印证×2 − 反证×3 + 新鲜度（30 天线性衰减）；反证累计 3 次直接淘汰。

## 2. 设计原则

1. **语义判断全部交 LLM，脚本只做簿记**。事实提炼、套路归纳、检索词、同义/合并/矛盾判定、印证与反证判定都在 LLM 侧；脚本只负责计数、预算、排序、落盘、逐字精确去重。把语义写成规则 + 参数在本项目被反复证伪（objective 全等匹配、N=3 晋升形同虚设、`entry_id` 真机从未生效、语义去重阈值调三轮仍漏），全部出自同一类错误。
2. **精确步骤是机器资产，引导型文字是模型资产**。
3. **注入只进一次 + 预算硬上限**：常驻块只放高相关内容，其余按需加载。
4. **写入端节流优于事后淘汰**：`FACTS_PER_RUN_MAX=3` + 同 App 冷却 300s。
5. **机制迁移必须重新校准**：借鉴 ≠ 照搬参数；跨场景复用未经验证视为假设，不得进主线。
6. **验证状态逐条标注**：✅已实测 / ⚠️方向一致未显著 / ❌未验证。
7. **总步数是弱判据**：轨迹约 40% 是 observe，确认/观察步淹没差异；判定用 Mann-Whitney，n≥5 起步。

## 3. 真机验证结果链

### 3.1 重构前：注入形态问题（10-01 前）

B（有知识）反而劣于 A（20.8 vs 18.4 步）；objective 原文占注入块约 60%（2207 字符），`type_text` 原值注入，`_WEAKEN_HINT`"以实际观测为准"等于授权重探索。max_steps=26 制造假数据（放大预算后 10/10）。

### 3.2 首轮重构对照（n=10/组，冻结快照）

三口径全部不显著（总步 p=0.65）。教训：①组内方差 13~103 步（7 倍）远大于效应量；②A 组清零要防异步蒸馏写回，B 组必须冻结快照防漂移。

### 3.3 知识被采纳 ≠ 执行干净

对既有 20 条轨迹回溯：`first_action_hit`=0.90、`path_prefix_hit`=1.00、`used_skill_tool`=0.90、`inject_hit`=1.00。步数分布由纠错/确认次数决定。

### 3.4 高知识密度任务：DoD4 达成（T3 时钟，n=12/组）

| 口径 | A 中位 | B 中位 | 中位差 | p |
|---|---|---|---|---|
| 总步数 | 35.0 | 14.0 | **−60.0%** | **0.0225** |
| 确认步数 | 17.0 | 7.0 | **−58.8%** | **0.0092** |

知识收益取决于任务的知识密度（T5 简单任务存在天花板效应）；播种曲线 62→36→16 步。

### 3.5 语义去重与容量治理

- **语义去重全部由 LLM 判定**，无 brain 时只做逐字精确去重；写入时合并（新增 vs 存量）与 compact（存量互判）共用同一判定。规则版实现（重叠率阈值 0.35/0.25/0.55/0.20、控件 id 正则、CJK bigram 指纹、贪心同义聚类、"包名或控件出现即印证"）整套删除。
- 容量滑动窗口（簿记）：tasks **283 → 50 run，16.7 MB → 3.6 MB**；失败 run 反证扣分（`fails×−3`，3 次淘汰）。

### 3.6 四臂验收（T3，n=5/臂，20/20）

A 无知识 / M 只记忆 / S 只技能 / B 都有；交错执行、每 run 前重置臂基准、每 run 后归位。

| 臂 | 中位 | 均值 | vs A |
|---|---|---|---|
| A | 41 | 43.0 | 基线 |
| **M** | **21** | **20.4** | **p=0.0216（−49%）** |
| S | 32 | 31.0 | p=0.076 |
| B | 40 | 38.8 | p=0.46 |

判定：①记忆有效且方差最小；②技能被 5/5 消费但不显著——**消费 ≠ 受益**；③B 掉回 A（注入块 1735→2475 字符，技能段挤掉好内容）——**常驻块塞平庸内容有净伤害**。

**A/M 三轮复现**：

| 轮次 | n | A 中位 | M 中位 | 中位差 | p |
|---|---|---|---|---|---|
| 四臂 | 5 | 41 | 21 | −49% | 0.0216 |
| 三臂 | 5 | 39 | 30 | −23% | 0.17 |
| A/M 专测 | 10 | 38.5 | 31.0 | −19.5% | 0.345 |

⇒ "记忆显著有效"降级为**方向三次一致为正、显著性不稳**。M 臂分布双峰（12/19/27 与 52/56 并存）：帮很多与没帮还偏高同时存在。

### 3.7 技能生产端修复与形态对照

- 修复：`validate_skill_summary` 硬性要求 `raw["name"]` 而 prompt 只产 `routine` ⇒ 技能恒空（skills_created=0）。修复为 name 回退 routine；真机随即产出干净的 11 步套路。
- 验收（A/M/S × n=5）：A 39 / M 30（p=0.17）/ S 36（p=0.68），「S ≥ M」未达成。
- 形态对照（同一技能文件，唯一差别是 playbook 行，n=10）：

| 臂 | 中位 | 均值 | 成功 |
|---|---|---|---|
| 动作序列经 load_skill | 41 | 48.3 | 9/10（一次 120 步触顶） |
| **playbook 经 load_skill** | **38** | **37.6** | 10/10 |
| playbook 进常驻注入块 | 45 | 51.0 | 5/5，更差 ⇒ 已回退 |

p=0.273，⚠️三处方向一致（均值 −22%、成功率满员、零灾难重放）。P2 差于 P 加固了"套路只走按需加载"。

### 3.8 文献对齐：自蒸馏技能无效不是个别现象

| 系统 | 技能表示 | 获取 | 验证 | 报告效果 |
|---|---|---|---|---|
| Voyager | 可执行代码库 | Agent 自写 | 环境执行 | 长任务里程提升 |
| ASI（arXiv:2504.06821） | 程序化技能 | 交互中归纳 | **程序化验证** | 比静态基线 +23.5pp；比"文本技能"+11.3pp |
| Agent Skills 规范 | `SKILL.md` 文本 | **人写** | 无 | SkillsBench +16.2pp，但 16/84 任务负增益；**自蒸馏 −1.3pp** |
| AWM / ExpeL | 自然语言 workflow / 洞察 | 从轨迹归纳 | 无 | web / 经验型任务提升 |
| Memp | 双粒度（脚本 + 轨迹） | 从轨迹归纳 | 无 | 混合最优；纯轨迹只在近重复任务有效 |
| ACE（ICLR 2026） | 演进式 playbook | 生成→反思→策展 | 反思 | +10.6%，token 成本下降 |

关键两条：**人写 +16.2pp vs 自蒸馏 −1.3pp**（我们的结果与后者一致）；**ASI 的 +11.3pp 来自"程序化 + 可验证"** ⇒ 收益来自表示与验证，不是更好的措辞。

### 3.9 实验设计的三个错误（复盘）

1. **把同一处理当成两个处理**：事实与技能都是 prompt 文字、来自同一次蒸馏，"事实有效、技能无效"无法区分类别差异与形态差异。
2. **题面里写了流程提示**：T3 的 objective 含约 600 字符的 `Flow notes / Navigation tip`，等于把技能层本该提供的隐藏规则直接告诉模型，技能层被自己中和掉。
3. **对照臂被脚本数据污染**：首轮 S 臂 5/5 加载的是旧机械技能（objective 全等匹配排到 top-1）。⇒ 机械技能数据自此不再使用，旧快照（`clock_llm` / `clock_form_*` / `post_lu`）作废。

### 3.10 2×2 实验：环境反馈带宽 × 知识（n=5/格，20/20）

操纵：`observe` 骨架**去掉 view_id**（文本、坐标、可点性保留）= 低带宽；开关 `files/flags/low_bw`。

| 臂 | 中位 | 均值 | 数据 |
|---|---|---|---|
| A 高带宽·无知识 | 36 | 37.0 | 41/27/30/51/36 |
| M 高带宽·有知识 | 33 | 32.8 | 43/39/33/27/22 |
| AL 低带宽·无知识 | 29 | 38.4 | 28/27/52/56/29 |
| ML 低带宽·有知识 | 44 | 44.0 | 44/36/53/41/46 |

高带宽知识 −4.2 步（p=0.53）；低带宽知识 **+5.6 步**（p=0.47）；交互项约 +9.8 步，**与"反馈越少知识越值钱"方向相反**。

机制：反馈带宽假设指的是"领域约定"这类环境给不了的知识，而我们库存九成是**控件 id 知识**；抹掉 view_id 等于把知识锚点一起抹掉。附带发现：**低带宽无知识 AL 中位 29 < 高带宽 A 的 36** ⇒ 这些 App 靠文本 + 坐标即可操作，view_id 非必需品，id 知识本就是冗余。

⇒ **知识能否发挥作用，取决于知识类型与环境锚点接口是否匹配。**

### 3.11 约定型知识：能产出多少（性质测试，非步数对照）

工具 `harness/experiments/_convention_probe.py`（离线蒸馏 + LLM 判定）。两项必要的原料修正：

1. `curator._trajectory_digest` 原只输出 `observe -> ok`，**控件树被整个丢掉**，而约定型知识只存在于界面状态里 ⇒ 探针自建"动作（脱敏）+ 界面状态摘要（可见文案 / 可点控件 / 焦点控件，**不含 id 与坐标**）"。
2. 题面不给 id，模型无法抄锚点，产出性质可直接归因。

**测试一 · 换题目**（13 / 11 条轨迹，同 judge）：

| 题目 | 条目 | 约定型 | 文本锚定 | 控件 id 锚定 | 交白卷轨迹 |
|---|---|---|---|---|---|
| 约定型题目 | 15 | **13（87%）** | 1 | **0** | 6（46%） |
| 现状题目（"环境事实 / UI 陷阱"） | 44 | 19（43%） | 1 | **24（55%）** | 0 |

⇒ 此前"九成锚点型"很大程度是**题面逼出来的**。另发现"配额驱动的幻觉"：现状题目在任何轨迹上都能交 2~5 条，其中 23% 被判无证据支撑。

**测试二 · 补一个漏掉的类别**（同批 4 条轨迹，配对 n=3/臂）。读真机产物发现，唯一一条跨 App 规律（截图因 projection 未启动失败 → 改用控件树观察）来自**工具层**，而题面全在讲界面控件。只补"工具/系统行为规律"这一类别定义（工具可用性前提、输入工具生效前提、观察手段分工、动作键语义、平台层怪癖），措辞一字不动：

| 题目 | 唯一存量（跨轨迹 LLM 归并后） | 交白卷轨迹 |
|---|---|---|
| 约定型（仅界面形态示例） | 2 / 1（n=2） | 3/4、3/4 |
| **约定型 + 工具/系统类别** | **4 / 6 / 4（n=3）** | **1/4、1/4、1/4** |

3/3 次高于对照的 2/2 次，两区间无重叠。机制性证据（同一现象的两种抽象层级）：

- 对照：「**时间选择器**弹出后若处于文本输入模式，键入需先点中小时/分钟框才生效」= 界面形态
- 补类别后：「**文本输入工具**在目标输入框未获焦点时**静默无效（不报错也不产生内容）**，必须先点击该输入框使其聚焦」= 工具层，跨 App 成立

补类别后还捞到前四批都没出现的经典界面约定：「新建条目插入列表**最前**（倒序）」「单选项弹窗选中条目本身不关闭，必须再点底部『确定』才提交」「系统级对话框『确定』右下、『取消』左下」「返回键在弹窗/子页面的语义是关闭当前层并回到上一级」。

⇒ **约定的真实形态是"工具/系统层的抽象规律"，不是控件级描述。**（此前判定"瓶颈在轨迹本身"被此轮推翻：缺的是类别定义，不是轨迹，也不是措辞。）

限制：唯一存量 4~6 条 / 4 条轨迹仍属稀疏；真正跨 App 的条目集中在工具层，界面层条目多与本批 App 的模态交互相关，**跨 App 泛化性未验证**。

| 4 | 容量三层设限：注入层硬上限、结构层效用排序、证据层归档 | §3.5 |
| 5 | 弱化措辞是行为参数（"以实际观测为准" = 授权重探索） | §3.1 |
| 6 | 判据用有效步 / 首动作命中率；max_steps 过小制造假数据 | §3.2/3.3 |
| 7 | embedding 当前不上：先结构容量后检索；触发条件 = 池子数十条 + 跨 App 泛化 | 池子 1 条时排序无差别（实测） |

一句话：**先给知识定上限，再让效用决定谁留下**——归并率不完美也能自洽。

## 6. 本轮定稿（2026-10-02/03）

### 6.1 语义判断全部 LLM，脚本只做簿记

红线：**任何语义判断不得写成规则 + 参数**。已连根删除：重叠率阈值四档（0.35/0.25/0.55/0.20）、控件 id 正则、CJK bigram 指纹、贪心同义聚类、"包名或控件出现即印证"、`objective[:40]` 写死技能名、机械转录 `from_run_record`、`score_skill` 打分、`promote_or_insert` 字符串匹配链、`find_by_pattern`。

替换实现（无 brain 一律降级为"不判断"，不猜）：

| 环节 | LLM 判定 | 无 brain 时 |
|---|---|---|
| 事实去重（新增 vs 存量） | `llm_dedup`：duplicate / merge+重写 / independent | 只做逐字精确去重 |
| 事实去重（存量 compact） | `llm_dedup_pool`：drop + rewrite | 同上 |
| 印证 / 反证 | `llm_marks`：勾选条目 | 什么都不做 |
| 检索选档 | `select_skills` / `search_skills` | 保持原序，不做相关性判断 |

脚本保留的簿记：计数与命中计数、预算与上限、效用分排序、逐字精确去重、落盘。

### 6.2 同一轮关掉的测量缺口

- **fact 级注入留痕**：knowledge 事件新增 `facts` 清单（此前只有 `memory: bool`）。
- **事实的 App 归属**：写入时直接落本次 run 的包名进 `fact_meta.json`，不再靠文本正则抽包名。
- **真机验证**（Clock T3）：清零基线 19 步成功、带知识 26 步成功，`load_skill` 被真实调用，fact 归属与印证计数均有值。

### 6.3 明确不做的事

- 不再把动作序列形态的技能拿来做对照实验（四轮数据一致否定）。
- 不再为语义判断新增阈值、正则或权重；需要新判断就加一次 LLM 调用。
- 不做 embedding（触发条件：池子 ≥ 数十条且需跨 App 泛化）。
- 不做迁移兼容、不做知识清理类自动化（用户直接操作磁盘）。

### 6.4 知识按"锚点依赖"分类（替代原"事实 / 技能"二分）

| 类型 | 定义 | 生效条件 | 库存 |
|---|---|---|---|
| **锚点型** | 依赖可寻址接口（view_id / 坐标） | 环境提供该锚点时 | 九成 |
| **约定型** | 不依赖具体控件的行为规律（键盘遮挡保存按钮、列表倒序、输入工具需先聚焦） | 任何环境 | 稀疏（4~6 条 / 4 轨迹，§3.11） |

定案：知识层按"是否依赖锚点"分类，不按"事实 / 技能"分平面。锚点型在高带宽环境小幅有效（方向三次一致为正）；约定型是唯一可能放大价值的一类，产出取决于**题面是否显式给出该类别** + 轨迹里有没有可沉淀的状态演化。

### 6.5 仅存的设计取舍（无需再讨论）

- **事实常驻注入 + 技能按需 load**：读者不同（模型 vs 机器），形态随之不同。
- **无 brain 时不做语义判断**：宁可留重复（由容量淘汰兜底），也不猜。
- **验证状态逐条标注**：playbook 优于动作序列为 ⚠️（p=0.273），按"负结果重复出现即成立"处理，不再追加样本量。
- **技能平面改为人工维护**：否定的是"自动蒸馏"这个供给方式，不是技能平面本身；留口子——有了执行验证手段或换场景可重跑。
