# 文档与方案约定（hachimi / OmniAgent 通用）

> 新增设计文档 / 方案 / 里程碑条目时，按此执行。
> 每条附"来源"，说明它针对的是哪类问题，便于判断适用边界。

---

## 1. 平面准入三问

任何"存储平面 / 能力模块"要进设计文档，必须先回答：

1. **谁写**（生产者，文件:行号）
2. **谁读**（消费者，是否被注入 / 被检索 / 被 UI 消费）
3. **读不到会怎样**（缺失时是零注入、降级，还是报错）

**答不上任意一条 ⇒ 不写进设计，或标注为"死平面待处置"。**

*来源*：审计发现若干平面处于"有消费者无生产者"或"有 API 无调用"状态，
长期被误认为已实现。三问用于在设计阶段就暴露这类问题。

## 2. 机制复用纪律：借鉴 vs 滥用

判断标准：**拿到新场景后，有没有重新校准并验证。**

- **借鉴**（可接受）：复用思想，但按新场景的实测样本重新定阈值与触发条件，并标注"初始值待校准"
- **滥用**（禁止）：把为 A 设计的机制直接搬到 B，沿用原参数且从未在 B 上验证

*来源*：某晋升机制原为 skill 设计，迁移到 memory 时沿用未校准的阈值，
而它在原场景也因匹配逻辑缺陷从未生效 —— 一个从未工作过的机制被搬到另一个场景。

## 3. 预留机制：只留文档，不实现代码

暂时用不上的机制只写设计说明，并写明启用条件。

*来源*：避免留下"看起来可用、实际无人调用"的空壳代码（与第 1 条同源）。

## 4. 验证状态逐条标注

| 标记 | 含义 |
|---|---|
| ✅ 已实测 | 有真机 / 真实场景数据，附样本量与出处 |
| ⚠️ 部分验证 | 仅单测覆盖，或真机未出现对应场景 |
| ❌ 未验证 | 机制已实现但从未在真实场景运行 |

**规则**：未验证的差异只能写成"设计差异"，不得表述为优势。
任何对外主张（含"更优""可反哺上游"）都必须能指向一条实测数据。

*来源*：若干机制在文档中被描述为改进，但缺少可引用的实测数据。

## 5. 「明确不做的事」单独成节

方案文档必须包含此节，与"待定项"并列，记录已被否决的方案及其理由。

*来源*：已被否决的方案容易在后续讨论中被重复提出。

## 6. 实验预注册

对照实验开始前先写清：研究问题（RQ）、判据口径、样本量、分组方式。
结论只对预注册时定义的指标负责。参见 `doc/preregistration_v1.3.md`。

*来源*：避免事后挑选显著指标。

## 7. 第三方参考与署名

- **思想借鉴（未复制代码）**：在方案的「参考与致谢」写清 项目名 + 仓库地址 + License +
  **借鉴了什么 / 没借鉴什么 / 我们的差异（附验证状态）**；**不写进 LICENSE 或版权头**
  （那会被引申为代码复用）。
- **代码级复用**：必须按其许可证保留版权声明与许可证文本（MIT ⇒ 保留即可，
  建议加 `THIRD-PARTY-NOTICES.md`，不改动自身 LICENSE）。
- 参数若参照他人形态，在命名处注释标明来源与"初始值待校准"。

*来源*：区分思想借鉴与代码复制的许可义务。

## 8. 数值必须标注校准状态

文档中的每个阈值 / 上限 / 触发间隔都要写清：

- 是**实测校准**还是**初始建议值**
- 校准样本是什么（设备、任务、样本量）
- 未校准的一律标注"待校准"

*来源*：未标注来源的阈值在后续维护中无法判断是否可信。

## 9. 区分事实、判断与待定

- **事实**：可核验（文件:行号、实测数据），不加修饰
- **判断**：标注理由与依据；无依据的明确写"待验证"
- **待定**：集中放进"待定项"，不混在正文

对比性表述须显式声明比较基准与场景（例："在手机端每步重发的成本结构下…"），
避免被读成对其他方案的优劣评价。

*来源*：同一设计在不同成本结构下结论相反，缺少场景基准容易产生误读。
